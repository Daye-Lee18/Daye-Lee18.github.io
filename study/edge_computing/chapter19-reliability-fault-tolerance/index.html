Chapter 19. Reliability & Fault Tolerance

Goal: Robot system에서 failure가 언젠가는 발생한다고 가정하고, 문제가 생겼을 때 얼마나 안전하게 버티고, 복구하고, 계속 동작할 수 있는지 이해한다.

Fault, Error, Failure, Redundancy, Watchdog, Retry, Timeout, Graceful Degradation, Fail-Safe, Fail-Operational, Single Point of Failure, Recovery, Redundant Sensor의 개념을 실제 robot architecture와 연결하는 것이 목표다.

1. Reliability란?

Reliability는:

시스템이 일정 기간 동안 요구된 기능을 정상적으로 수행할 가능성

과 관련된 개념이다.

쉽게 말하면:

얼마나 잘 안 고장나는가?

이다.

하지만 실제 robot system에서는:

고장이 절대 안 남

을 기대하기 어렵다.

그래서 더 중요한 질문은:

고장이 나면 어떻게 되는가?

이다.

2. Fault Tolerance

Fault Tolerance는:

일부 component에 문제가 생겨도 전체 system이 계속 기능하거나 안전하게 동작할 수 있도록 만드는 능력

이다.

예:

Camera 1 failure
     ↓
Camera 2 available
     ↓
Perception continues

이런 구조가 fault tolerant하다.

3. Fault, Error, Failure

세 단어는 비슷하지만 구분하면 좋다.

Fault
→ 문제의 원인

Error
→ 내부 상태가 잘못된 상태

Failure
→ 외부에서 요구 기능을 수행하지 못한 결과

4. 예시

LiDAR cable이 빠졌다고 하자.

Fault
→ Cable disconnected

그 결과:

Error
→ No LiDAR data

그리고:

Failure
→ Localization unavailable

가 될 수 있다.

5. 또 다른 예

SSD가 망가졌다고 하자.

Fault
→ Storage hardware fault

Error
→ Write operation fails

Failure
→ rosbag recording unavailable

이다.

6. Reliability와 Fault Tolerance는 다르다

Reliability
→ 고장이 얼마나 적게 발생하는가?

Fault Tolerance
→ 고장이 발생해도 얼마나 버틸 수 있는가?

이다.

둘 다 중요하다.

7. Robot은 복잡한 System이다

Vision60 같은 robot은:

Battery
Motors
MCU
Jetson
LiDAR
IMU
Camera
Network
Storage
ROS 2
SLAM
Navigation

많은 component로 이루어진다.

Component 수가 늘어날수록 failure point도 많아진다.

8. Single Point of Failure

어떤 하나의 component failure가 전체 system failure로 이어지는 경우:

Single Point of Failure

라고 한다.

예:

Single Power Supply
       ↓ failure
Entire Compute Down

9. SPOF

Single Point of Failure를 줄여:

SPOF

라고도 한다.

시스템 설계에서는:

Where is the SPOF?

를 찾는 것이 중요하다.

10. 예: LiDAR 하나만 사용하는 SLAM

LiDAR
   ↓
SLAM
   ↓
Localization

LiDAR가 죽으면:

Localization lost

가 된다.

이 경우 LiDAR는 중요한 SPOF일 수 있다.

11. Redundancy

같은 기능을 수행할 수 있는 component를 여러 개 두는 것을:

Redundancy

라고 한다.

예:

Sensor A
Sensor B

한 sensor가 실패해도 다른 sensor를 사용할 수 있다.

12. Hardware Redundancy

예:

Dual IMU
Dual Network Link
Dual Power Supply

같은 구조가 hardware redundancy다.

13. Software Redundancy

Software에서도 redundancy를 사용할 수 있다.

예:

Primary localization
Backup localization

또는:

Algorithm A
Algorithm B

결과를 비교할 수 있다.

14. Redundancy가 항상 좋은 것은 아니다

장점:

Reliability ↑
Fault tolerance ↑

하지만:

Cost ↑
Weight ↑
Power ↑
Complexity ↑
Maintenance ↑

도 증가한다.

Robot에서는 특히 weight와 power가 중요하다.

15. Active Redundancy

두 component를 동시에 사용한다.

예:

IMU A
IMU B

둘 다 계속 측정한다.

한쪽 문제가 발생하면 즉시 다른 쪽을 사용할 수 있다.

16. Standby Redundancy

평소에는 primary만 사용한다.

Primary
active

Backup
standby

Primary failure 시 backup을 시작한다.

17. Hot Standby

Backup이 이미 실행 중이어서 빠르게 전환 가능:

Primary
ACTIVE

Backup
READY

18. Cold Standby

Backup은 평소 꺼져 있다.

Failure 후:

Start Backup

하므로 복구 시간이 더 길 수 있다.

19. Fault Detection

Fault tolerance를 하려면 먼저:

문제가 생겼다는 것을 알아야 한다.

즉:

Fault Detection

이 필요하다.

20. Detection Example

LiDAR:

Expected:
10 Hz

Actual:
0 Hz

이면 fault를 감지할 수 있다.

21. Fault Isolation

문제가 있다는 것만으로는 부족하다.

어디가 문제인지 좁히는 과정:

Fault Isolation

이다.

예:

LiDAR hardware?
Network?
Driver?
ROS?
FAST-LIO2?

22. Fault Identification

좀 더 구체적으로:

What exactly failed?

를 판단한다.

예:

Ethernet cable disconnected

처럼 원인을 특정한다.

23. FDI

이 세 개를 묶어:

Fault Detection and Isolation

또는 넓게:

Fault Detection and Identification

이라고 부르는 경우가 있다.

24. Health Monitoring

Chapter 18에서 배운 observability가 fault detection의 기반이 된다.

예:

LiDAR Hz
IMU Hz
CPU Temp
Disk Usage
Process Heartbeat

을 계속 확인한다.

25. Heartbeat

Component가 살아 있음을 주기적으로 알리는 signal:

Heartbeat

이다.

예:

FAST-LIO2
    │
    │ 10 Hz heartbeat
    ▼
Health Monitor

26. Heartbeat Timeout

예:

Expected:
heartbeat every 100 ms

No heartbeat for:
500 ms

이면:

Component failure suspected

로 판단할 수 있다.

27. Timeout

Timeout은:

일정 시간 동안 응답이 없으면 더 이상 기다리지 않고 failure로 판단

하는 mechanism이다.

28. Network Timeout

예:

Send Command
   ↓
Wait for Response
   ↓
No response for 1 s
   ↓
Timeout

29. 왜 Timeout이 필요한가?

Timeout이 없으면:

Wait forever

가 될 수 있다.

하나의 component failure가 전체 pipeline을 멈추게 할 수 있다.

30. Timeout 값을 너무 짧게 잡으면?

정상적인 network jitter에도 failure로 판단할 수 있다.

False Positive

가 증가한다.

31. Timeout을 너무 길게 잡으면?

실제 failure를 늦게 감지한다.

Failure Detection Delay ↑

따라서 실제 timing requirement를 기반으로 설정해야 한다.

32. Retry

작업이 실패했을 때 다시 시도하는 것:

Retry

이다.

예:

Cloud upload failed
      ↓
Retry

33. Retry가 유용한 경우

일시적인:

Network glitch
Temporary server error
Packet loss

같은 문제에는 retry가 도움이 된다.

34. Retry가 위험한 경우

근본적으로 실패한 상황:

Wrong credential
Disk full
Hardware disconnected

에서 계속 retry하면:

CPU waste
Network flooding
Log flooding

이 발생할 수 있다.

35. Retry Limit

예:

Retry 3 times

후:

Declare failure

처럼 제한할 수 있다.

36. Exponential Backoff

Chapter 17에서 배운 것처럼:

1 s
2 s
4 s
8 s
16 s

처럼 retry interval을 늘릴 수 있다.

Server/network에 부담을 줄인다.

37. Jittered Backoff

Robot 100대가 동시에 reconnect하면 모두:

1 s
2 s
4 s

에 동시에 요청할 수 있다.

그래서 약간의 random delay를 추가할 수 있다.

예:

4 s ± random

38. Watchdog

Watchdog은:

System/component가 멈췄는지 감시하고 필요 시 recovery action을 수행

하는 mechanism이다.

39. Software Watchdog

예:

FAST-LIO2
   │ heartbeat
   ▼
Watchdog Process

heartbeat가 끊기면:

Restart FAST-LIO2

할 수 있다.

40. Hardware Watchdog

SoC/MCU에 hardware timer가 있을 수 있다.

Software가 주기적으로 watchdog을 reset해야 한다.

Software healthy
→ Feed watchdog

Software가 멈추면:

No feed
   ↓
Timeout
   ↓
System Reset

41. Watchdog Feed

주기적으로 watchdog timer를 reset하는 것을 흔히:

Feed the watchdog

또는:

Kick the watchdog

이라고 표현한다.

42. Watchdog의 문제

잘못 설계하면:

Crash
Restart
Crash
Restart

무한 restart loop가 생길 수 있다.

43. Restart Storm

여러 service가 서로 dependency가 있는데 계속 재시작하면 system 전체가 불안정해질 수 있다.

이를 흔히:

Restart Storm

이라고 부를 수 있다.

44. Restart Backoff

예:

1st restart → immediate
2nd → 5 s
3rd → 30 s
4th → stop and alert

같은 정책을 사용할 수 있다.

45. Recovery

Failure 후 정상 상태로 돌아오는 과정:

Recovery

이다.

46. Recovery Level

Recovery는 여러 단계로 할 수 있다.

Level 1
Retry operation

Level 2
Restart node

Level 3
Restart container

Level 4
Restart service stack

Level 5
Reboot computer

Level 6
Operator intervention

47. 가장 작은 Recovery부터

가능하다면:

Restart entire robot

보다:

Restart failed component only

가 좋다.

왜냐하면 영향 범위가 작기 때문이다.

48. Blast Radius

Failure나 recovery가 영향을 미치는 범위를:

Blast Radius

라고 표현할 수 있다.

예:

Restart camera node
→ small blast radius

Reboot Jetson
→ large blast radius

49. Isolation

한 component failure가 다른 component로 퍼지지 않게 하는 것:

Fault Isolation

과 연결된다.

Docker/container 분리도 일부 도움이 될 수 있다.

50. Process Isolation

예:

Camera process crashes

해도:

FAST-LIO2
Navigation

까지 같이 죽지 않도록 process를 분리할 수 있다.

51. Container Isolation

예:

Perception Container
SLAM Container
Fleet Agent Container

를 나누면 dependency/failure 범위를 줄일 수 있다.

하지만 container가 완벽한 fault isolation을 보장하는 것은 아니다.

52. Resource Isolation

한 process가 모든 RAM을 사용하면 다른 process까지 죽을 수 있다.

그래서:

CPU Limit
Memory Limit
Queue Limit
Disk Quota

같은 resource isolation을 고려할 수 있다.

53. Memory Leak

Program이 memory를 계속 할당하고 해제하지 않으면:

Memory Leak

이 생긴다.

1 GB
2 GB
5 GB
10 GB
...

결국 OOM으로 이어질 수 있다.

54. Memory Limit

Container/process에 memory limit을 두면 system 전체를 보호하는 데 도움이 될 수 있다.

하지만 memory가 부족해 해당 component가 먼저 죽을 수 있으므로 recovery 설계와 함께 봐야 한다.

55. Disk Full Fault

Chapter 13에서 배운 것처럼 disk full은 흔한 failure다.

rosbag
Docker log
System log

가 계속 쌓이면 disk가 가득 찬다.

56. Disk Full을 Fault Tolerant하게 처리

예:

Disk > 80%
→ Warning

Disk > 90%
→ Stop optional recording

Disk > 95%
→ Preserve critical logs only

처럼 단계적으로 degrade할 수 있다.

57. Graceful Degradation

System 전체를 바로 멈추는 대신 일부 기능을 낮춰서 계속 동작하는 것:

Graceful Degradation

이다.

58. Example: Camera Failure

평상시:

LiDAR
Camera
IMU

모두 사용.

Camera failure:

LiDAR + IMU SLAM continues
Vision features disabled

이런 동작이 graceful degradation이다.

59. Example: Cloud Failure

Internet Lost

되어도:

Local SLAM
Navigation
Safety

는 계속 동작.

Telemetry Upload
OTA

만 중단.

60. Example: Disk Almost Full

Raw camera recording OFF
Critical logs ON
SLAM ON

처럼 중요한 기능을 우선한다.

61. Degraded Mode

기능이 일부 제한된 상태를:

Degraded Mode

라고 정의할 수 있다.

예:

NORMAL
DEGRADED
SAFE_STOP
ERROR

62. State Machine

Reliability system은 state machine으로 관리하기 좋다.

BOOT
 ↓
NORMAL
 ↓ fault
DEGRADED
 ↓ severe fault
SAFE_STOP

Recovery:

DEGRADED
 ↓ recovered
NORMAL

63. Fail-Safe

Failure가 발생하면:

안전한 상태로 가는 것

을:

Fail-Safe

라고 한다.

64. Example

Localization이 사라졌는데 robot이 계속 자율주행하면 위험할 수 있다.

Localization Lost
      ↓
Stop Autonomous Motion

이 fail-safe 동작일 수 있다.

65. Fail-Operational

Failure가 생겨도:

필요한 기능을 계속 수행

하는 것을:

Fail-Operational

이라고 한다.

66. Fail-Safe vs Fail-Operational

Fail-Safe
→ 문제가 생기면 안전하게 정지

Fail-Operational
→ 문제가 생겨도 기능을 계속 수행

이다.

67. 어떤 것을 선택할까?

Application에 따라 다르다.

예:

Construction Robot
Localization lost

라면 안전 정지가 더 적절할 수 있다.

하지만:

Aircraft flight control

처럼 즉시 멈출 수 없는 system은 fail-operational 요구가 더 강할 수 있다.

68. Safety와 Availability Trade-off

계속 동작하는 것이 항상 좋은 것은 아니다.

Availability ↑

를 위해 불확실한 sensor를 계속 사용하면 safety가 떨어질 수 있다.

69. Confidence-Based Degradation

예:

Localization confidence high
→ Normal

Confidence medium
→ Slow speed

Confidence low
→ Stop

같은 방식도 가능하다.

70. Redundant Sensors

예:

LiDAR
Camera
IMU
Joint Encoder

가 서로 다른 방식으로 motion/environment를 측정한다.

이런 heterogeneous redundancy는 유용하다.

71. Homogeneous Redundancy

같은 종류 sensor 여러 개:

IMU A
IMU B
IMU C

72. Heterogeneous Redundancy

다른 종류 sensor로 같은 state를 보완:

LiDAR
Camera
Leg Odometry

모두 robot motion에 대한 정보를 제공할 수 있다.

73. Common-Mode Failure

Redundant sensor를 두 개 달아도 둘이 같은 원인으로 동시에 죽을 수 있다.

예:

Two Cameras
     │
     └── Same power supply
              ↓ failure
       Both cameras lost

이를:

Common-Mode Failure

라고 한다.

74. Common-Cause Failure

하나의 공통 원인이 여러 component를 동시에 실패시키는 것을:

Common-Cause Failure

라고 한다.

예:

Overheat
Power loss
Water ingress
Network switch failure

75. Redundancy 설계 시 중요한 것

단순히:

2개 달기

가 아니라:

Independent Power?
Independent Network?
Different Failure Mode?

까지 생각해야 한다.

76. Sensor Voting

3개의 sensor가 있다고 하자.

Sensor A = 10.0
Sensor B = 10.1
Sensor C = 50.0

C가 이상하다고 판단할 수 있다.

이를 voting/consistency checking으로 처리할 수 있다.

77. Majority Voting

3개 component 중 2개가 같은 결과를 내면 그 결과를 선택하는 방식.

A → 1
B → 1
C → 0

Result → 1

78. Triple Modular Redundancy

세 개의 동일한 subsystem과 voter를 사용하는 구조를:

TMR
=
Triple Modular Redundancy

라고 한다.

Safety-critical system에서 볼 수 있다.

79. Robot에서는 항상 TMR을 쓰나?

아니다.

비용과 무게가 매우 크다.

Robot에서는 필요한 critical subsystem에 선택적으로 redundancy를 적용한다.

80. Plausibility Check

Sensor 값이 물리적으로 가능한 범위인지 확인할 수 있다.

예:

Robot speed:
500 m/s

이면 명백히 이상하다.

81. Range Check

예:

Battery voltage
Temperature
Joint angle

가 allowed range 밖이면 fault로 볼 수 있다.

82. Rate-of-Change Check

값 자체는 정상 범위인데 갑자기 너무 빠르게 바뀌는 것도 이상할 수 있다.

예:

Pose:
0 m → 100 m in 10 ms

83. Cross-Sensor Consistency

예:

IMU says robot stationary

Leg odometry says 5 m/s

이면 sensor 중 하나가 이상할 가능성이 있다.

84. Residual Monitoring

State estimator에서:

Prediction
vs
Measurement

차이를 residual로 볼 수 있다.

Residual이 갑자기 매우 커지면 sensor fault나 model 문제를 의심할 수 있다.

85. Covariance와 Health

Estimator의 covariance가 급격히 커지면:

State uncertainty ↑

를 의미할 수 있다.

이를 degraded mode trigger로 사용할 수 있다.

86. Localization Health Example

Position covariance small
→ Healthy

Covariance increasing
→ Warning

Localization invalid
→ Safe Stop

처럼 상태를 나눌 수 있다.

87. Fault Injection

Reliability를 테스트하려면 실제 failure를 일부러 만들어 볼 수 있다.

이를:

Fault Injection

이라고 한다.

88. Example Fault Injection

LiDAR cable disconnect
Camera disable
Network disconnect
Disk fill
Kill FAST-LIO2 process
CPU overload

등을 일부러 발생시킨다.

89. 왜 Fault Injection을 할까?

정상 상황만 테스트하면 recovery path를 검증할 수 없다.

질문:

LiDAR가 실제로 죽으면 robot은 어떻게 행동하는가?

를 실제로 확인해야 한다.

90. Chaos Engineering

Distributed/cloud system에서는 의도적으로 failure를 주입해 resilience를 검증하는 접근을:

Chaos Engineering

이라고 한다.

Robot에도 일부 개념을 적용할 수 있지만 physical safety를 매우 신중히 고려해야 한다.

91. Robot Fault Test는 안전하게

실제 robot에서 fault injection을 할 때는:

Robot secured?
Low speed?
E-stop available?
Human nearby?
Safe test area?

를 먼저 확인해야 한다.

92. FMEA

Reliability/safety 분야에서 많이 사용하는 방법:

FMEA
=
Failure Modes and Effects Analysis

이다.

93. FMEA의 핵심 질문

각 component에 대해:

어떻게 실패할 수 있는가?
그 failure의 영향은?
어떻게 감지할 것인가?
어떻게 대응할 것인가?

를 정리한다.

94. FMEA Example

Component Failure Mode Effect Detection Response
LiDAR Data loss SLAM degraded Topic 0 Hz Stop autonomy
Camera Frame loss Vision unavailable FPS 0 LiDAR-only mode
SSD Disk full Logging fails Disk >95% Stop optional logs
FAST-LIO2 Process crash No localization Heartbeat lost Restart once

95. Severity

101. MTBF

MTBF:

102. MTTF

Mean Time To Failure

이다.

103. MTTR

MTTR:

Mean Time To Repair

또는 운영 문맥에 따라 recovery 의미로 쓰이기도 한다.

여기서는:

Failure 발생 후 정상 복구까지 걸리는 평균 시간

으로 이해하면 된다.

≈

105. Availability와 MTBF/MTTR

매우 단순화하면:

Availability
≈
MTBF / (MTBF + MTTR)

관계를 생각할 수 있다.

즉:

고장을 줄이는 것
+
복구 시간을 줄이는 것

둘 다 availability를 높인다.

각 component마다 다음을 묻는다.

How can it fail?

How do we detect it?

How fast can we detect it?

What is the impact?

Can we continue without it?

Can we recover automatically?

What is the safe state?

What logs do we need?

218. Chapter 19 핵심

Reliable robot은:

절대 고장나지 않는 robot

이 아니다.

현실적으로는:

문제를 빨리 감지하고,
영향을 제한하고,
가능하면 자동 복구하고,
복구할 수 없으면 안전하게 동작하는 robot

이다.

즉:

Detect
+
Isolate
+
Recover
+
Degrade
+
Fail Safely

가 핵심이다.
